## Como o Power Pages funciona por baixo

[FATO] Power Pages roda sobre a stack do antigo Power Apps Portals: **Liquid (templating) + Bootstrap + jQuery + Dataverse**. Ele aceita HTML/CSS/JS customizado — mas com um lugar certo para cada coisa e **uma pegadinha (CSP)** que é o erro nº 1 de quem embute JS.

## A maneira mais prática (para um dashboard JS)

O caminho de menor atrito, todo dentro do **design studio**:

1. **HTML (o container):** na página, adicione uma seção e use **"Editar código" (`</>`)**. Coloque o markup do dashboard, ex.: `<div id="dashboard"></div>` + um `<canvas>`/`<svg>`.
2. **JS (a lógica do gráfico):** cada página tem um editor de **"JavaScript" próprio** (ícone `</>` no estúdio) — esse é o lugar **certo** para seu script (ele roda no load e **não é higienizado**, ao contrário do editor de texto rico, que remove `<script>`).
3. **Biblioteca de gráficos + dados:** suba como **Arquivos da Web (Web Files)** — `chart.min.js`, `dashboard.js`, `dados.json` — e referencie por caminho relativo. O portal serve esses arquivos estáticos direto.

⚠️ **A pegadinha — CSP (Content Security Policy):** dependendo da config de segurança do site, **scripts de CDN externo são bloqueados**. Duas saídas: (a) **subir a lib como Web File** (recomendado — evita CSP de vez), ou (b) **allowlistar o domínio do CDN** em *Configurações → Segurança → Content Security Policy*. Se um gráfico "não renderiza e o console acusa CSP", é isso.

## Três métodos, do mais simples ao mais robusto

| Método | Como | Quando usar |
|---|---|---|
| **A — Inline self-contained** | Cola HTML+CSS+JS+lib **tudo embutido** numa seção via "Editar código" | Validação rápida; igual ao seu `index.html` de hoje, só que com JS. Atualizar = recolar |
| **B — Web Files + fetch** | Lib/JS/CSS como Web Files; página tem `<div>` + `<script src>`; dados num `dados.json` | Produção leve. Atualizar dados = trocar **um** arquivo |
| **C — `pac` CLI + VS Code** | `pac pages download/upload` versiona o site como código; seu pipeline Python gera os assets e dá `pac pages upload` | **Encaixa no seu fluxo atual** (Python + CI). Versionável, automatizável |

## Recomendação para o seu caso

Como vocês já têm um **pipeline Python gerando os dados**, o fim de jogo mais saudável é o **Método C**: o script Python escreve `dashboard.js` + `dados.json`, e um `pac pages upload` empurra pro site (dá pra rodar no mesmo GitHub Actions que já atualiza o histórico). Mas para **começar e validar agora**, o **Método A** (inline) leva minutos.

## Dois pontos que continuam valendo

- **Visibilidade "Particular":** o site exige login do tenant (foi o que você viu no SSO). O dashboard ficaria visível a usuários autenticados do ColaboraGov. Tornar **público** é outra config (e provavelmente passa por admin/licença + governança SGD).
- **Dado sensível:** continua sendo base de servidores federais — aqui, atrás de login do tenant, é bem mais adequado que o GitHub Pages público de hoje.
